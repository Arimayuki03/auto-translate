### E-001 测试主 API 返回 401/403 鉴权失败
- 来源：background / provider（openai）
- 复现步骤：设置页填 OpenAI 兼容 API（BaseURL `https://tokenrhythm.studio/v1`、模型 `deepseek-v4-flash-0731`、真实 Key）→ 点「测试主 API」
- 错误内容（原始日志）：
  ```
  主 API连接失败：鉴权失败（401/403）：请检查 API Key
  [auto-translate] API 请求失败  鉴权失败（401/403）：请检查 API Key
    postJson @ http.ts:119
    chat @ openai.ts:13
    testConnection @ index.ts:105
  ```
- 次数：1
- 状态：**已搁置**（用户决定不深究）。已确认**非插件回归**：URL 拼接、请求格式、错误诊断均正确；属 tokenrhythm 服务端对浏览器扩展类请求的 CSRF 拦截。curl 得 401、插件得 403 CSRF，触发头未最终定位（已排除 Origin/Sec-Fetch/UA/Cookie/Referer 单独作用）。后续如需支持该服务商，再评估 `declarativeNetRequest` 剥离请求头等方案。
- 诊断对象（用户展开后提供）：
  ```json
  {
    "provider": "openai",
    "endpoint": "https://tokenrhythm.studio/v1/chat/completions",
    "hostname": "tokenrhythm.studio",
    "status": 403,
    "responsePreview": "{\"code\":\"CSRF_INVALID\",\"message\":\"请求安全校验失败，请刷新页面后重试\",\"traceId\":\"trace_a6a67cb7-…\"}",
    "code": "auth"
  }
  ```
- 结论：
  - 服务器因 **CSRF_INVALID（请求安全校验失败）** 拒绝，属**网页应用的安全拦截**，发生在检查 API Key 之前 → 与 Key 是否有效无关。
  - `https://tokenrhythm.studio/v1` 疑似**网站/控制台地址而非无状态 API 端点**；纯 API 不会做 CSRF 校验。
  - 插件侧表现全部正确：URL 拼接正确、请求格式标准、错误诊断准确（403 + 抓到服务器原始返回 + 标 auth 来源）。
- 后续建议（非插件 bug，供用户排查）：
  - 到 tokenrhythm.studio 控制台确认**正确的 API 端点地址**（可能是独立的 api 域名）。
  - 若该服务商确对程序化请求做 WAF/CSRF 拦截，则属服务端限制，插件无法也不应绕过。

#### 补充取证：curl 对比探测（2026-08-10）
用户提供了 tokenrhythm 官方 API 文档，证实端点无误：
- OpenAI 对话 = `POST /v1/chat/completions`，统一基础地址 = `https://tokenrhythm.studio/v1`
- → 插件拼出的 `https://tokenrhythm.studio/v1/chat/completions` **与官方文档完全一致**，URL 拼接正确。

用**假 Key** 做 curl 对比探测（不触碰用户真实 Key），结果：

| 探测 | 附加请求头 | 服务器返回 |
|------|-----------|-----------|
| T1 POST 基础 | 仅 Auth+ContentType | `401 UNAUTHORIZED`「未认证或登录已过期」 |
| T2 GET /v1/models | 仅 Auth | `401 UNAUTHORIZED` |
| T3 POST | + `Origin: chrome-extension://…` | `401 UNAUTHORIZED` |
| T4 POST | + `Origin: https://some-random-website.com` | `401 UNAUTHORIZED` |
| T5 POST | + Origin + `Sec-Fetch-*` | `401 UNAUTHORIZED` |
| T6 POST | + 浏览器 User-Agent | `401 UNAUTHORIZED` |
| T7 POST | + 伪造 session Cookie | `401 UNAUTHORIZED` |
| T8 POST | + Referer | `401 UNAUTHORIZED` |

**关键对比：**
- curl（各种头组合）→ 一律 `401 UNAUTHORIZED`（正常的"Key 无效"响应，说明请求走到了鉴权检查）
- 插件（真实 Key，浏览器环境）→ `403 CSRF_INVALID`（在鉴权之前就被安全校验拦截）

**已排除**（单独加都不触发 CSRF）：Origin、Sec-Fetch-*、浏览器 UA、Cookie（伪造）、Referer。

**当前最可能假设：** 触发 CSRF 的是「**真实登录会话**」。CSRF 防护的本质是"携带有效会话的请求必须附带 CSRF token"。若用户在同一浏览器登录过 tokenrhythm.studio 网页控制台，扩展请求（manifest 为 `<all_urls>` host 权限）可能带上了**有效会话 Cookie** → 服务器判定"有会话→需 CSRF token"→ 拦截。curl 不带/带无效 Cookie → 被当作无状态 API 调用 → 直接查 Key。此假设待用户确认登录状态后验证。

**待定方向（未实施，需用户同意才开始）：** 若确认为会话 Cookie 触发，可评估用 `declarativeNetRequest` 在请求发出前剥离 Origin/Cookie，或引导用户避免在同浏览器登录控制台；具体是否做、怎么做，待「开始修复」指令。

### E-002 内容脚本大页面卡顿/无响应 —— 【已定位真因并修复】
- **真正根因（靠 [IT-PERF] 埋点实测定位，非猜测）**：**视口懒翻译彻底失效**。
  `observeLazy` 的 IntersectionObserver 回调**漏判 `entry.isIntersecting`**。IO 首次回调会把**所有被观察目标**都派发为 entries（含屏幕外、`isIntersecting=false` 的），旧代码不加判断地**全部 unobserve + 全部入队** → 60ms 后一次性翻译/占位全部单元。
- **实测数据（en.wikipedia.org，[IT-PERF]）**：
  ```
  待译单元=1012
  reserve 51 个占位  wall=14.8ms   (0.29ms/个)
  reserve 961 个占位 wall=2752.9ms (2.86ms/个) ← 屏幕外 961 个被一次性占位，卡 2.75 秒
  ```
  本应只译视口内约 51 个，结果屏幕外 961 个也立刻全译 → 主线程被约 2.75 秒占位/渲染占满 → 无响应。
- **修复（engine.ts `observeLazy`）**：回调加 `if (!entry.isIntersecting) continue;`，只处理真正进视口的单元，屏幕外的保持观察、滚进来才译。修复后初始只占位/翻译视口内约 51 个（约 15ms），其余随滚动分批，页面不再冻结。
- **回归测试**：`tests/lazyViewport.test.ts`（3 例，mock IntersectionObserver，验证 isIntersecting 门控）。
- **结论**：此前多轮优化（记忆化/时间片遍历/paced 渲染/会话取消）降低的是"单操作成本"，方向对但没命中根因——真正的问题是"一次干了 961 个的活"。决定性修复是 isIntersecting 门控；其余优化保留（叠加有益）。
- 状态：**已修复·待用户实机确认**。`[IT-PERF]` 埋点已于 2026-09-14 移除（isIntersecting 门控已由 `tests/lazyViewport.test.ts` 回归测试锁定，不再依赖埋点复测）。

### E-002a 前期排查记录与 modulepreload 警告
- 来源：content（构建产物/注入层）
- 复现步骤：DeepSeek 配置，打开 `en.wikipedia.org/wiki/Artificial_intelligence`，触发整页翻译（共 51 段，去重正常、N 不涨）。用户反馈「插件导致电脑特别卡」，页面控制台反复出现 preload 警告。
- 错误内容（原始日志，节选）：
  ```
  The resource chrome-extension://…/assets/modulepreload-polyfill-B5Qt9EMX.js was preloaded using link preload but not used within a few seconds from the window's load event. …
  The resource chrome-extension://…/assets/storage-CRAzfm9d.js was preloaded using link preload but not used …
  A preload for '…modulepreload-polyfill-B5Qt9EMX.js' is found, but is not used because it is a cross-world extension resource mismatch.
  A preload for '…storage-CRAzfm9d.js' is found, but is not used because it is a cross-world extension resource mismatch.
  ```
- 次数：多条、反复出现
- 状态：**已按 read-frog 模型重构·待用户复测**
- 用户确认（关键）：**卡顿只在翻译进行中**，翻译完成、页面稳定后不再卡（选项 A）；严重时 CPU 很高、浏览器无响应。
  → 排除"后台失控"（观察器死循环 / 监听器泄漏）。定性为**大页翻译的主线程重负载**。
- **最终方案：按用户指令，参照 read-frog-main 的翻译方法做性能重构**（见下方"read-frog 式重构"）。
- 前期已实施的基础修复（保留）：
  1. `getPageContext`（engine.ts）：原先**深克隆整个 body + 读 innerText**（长文页一次性阻塞主线程、innerText 强制整页排版）。改为 TreeWalker 原地遍历文本节点、`textContent` 取词（不触发排版）、跳过脚本/样式/自身 UI、**累加到 maxChars 即提前停止**，不再克隆、不再拼整页长串。
  2. `reserve` 布局抖动（engine.ts + renderer.ts）：原先逐段"插入占位 → 读 `clientWidth`"，而 `clientWidth` 会强制**整页重排**，51 段 ≈ 51 次整页重排交替 → 浏览器无响应主因之一。改为**写 DOM 前一次性预读所有容器宽度**（仅一次重排），占位阶段复用预读值（`reserve`/`estimateHeight` 增加 `preWidth` 参数），消除逐段重排。
  3. **`extractUnits` 样式计算风暴（extractor.ts，最重的一处）**：原先 `isExcluded` 对**每个文本节点的每一层祖先**都调 `isHiddenElement`→`getComputedStyle`，即 O(文本节点数×祖先深度) 次样式计算——大页面一次扫描就是几万次，观察器反复触发叠加成几十万级 → 浏览器无响应主因。修复：
     - `isHiddenElement` 结果按元素**记忆化**（`hiddenCache`），同一扫描内每元素只算一次；
     - `isExcluded` 的"自身或祖先是否排除"做**累计记忆化**（`excludedCache`），命中即短路，不再重复向上爬。
     - 样式计算量从 O(文本节点×深度) 降到 O(去重元素数)。
  4. **观察器自激扫描（observer.ts）**：原先 MutationObserver 回调忽略突变来源，我们自己的翻译渲染（插占位/包裹/回填/控件替换）也会触发整页重扫，翻译期间反复自激。修复：回调接收 `MutationRecord[]`，若本批突变**全部**源自我们注入的节点（带 `data-it-*` 属性或 `it-*` 类）则忽略；混入任何外部变化才照常调度。
- 其余已排查、暂不动的观察项：
  - preload 警告（Vite 代码分割 + 隔离世界 modulepreload 跨世界不匹配）属噪音，非卡顿主因，见下方独立条目。

### E-004 read-frog 式性能重构（应"直接参照 read-frog-main 的翻译方法重构"指令）
- 来源：content 引擎（engine.ts / extractor.ts / renderer.ts / observer.ts / translate.ts / scheduler.ts 新增 / background/index.ts / messages.ts）
- 状态：**已实施·107 测试全绿·待用户实机复测**
- 借鉴 read-frog 的"绝不让主线程一次性干大活"模型，移植以下骨架（保留本项目架构，未引入 React/WXT）：
  1. **`scheduler.ts`（新增）**：`yieldToMain()`（scheduler.yield → postTask → MessageChannel → setTimeout 降级链）+ `createWorkPacer`/`pauseIfBudgetSpent`（12ms 时间片）。
  2. **时间片遍历**：`extractUnitsChunked`（extractor.ts）——全页扫描分片执行，每花完 12ms 预算让出主线程；`translateAll` 改用它，还原（generation 变化）即中止。
  3. **paced 渲染**：`translateUnits` 的占位插入循环与 `renderBatch` 的回填循环都按预算让出（每 12ms），大页面几十个节点的 DOM 写不再堆在一个同步任务；每次让出后校验 generation，还原即中止。
  4. **会话取消**：`translate` 请求携带 `sessionId`（=引擎 generation）；background 按会话维护 `AbortController`，`TranslateService.translate` 接收 `AbortSignal`；还原/SPA 换页时 content 发 `cancel-translation`，background 批量 abort，中止错误静默返回（不当失败上报）。
- 叠加此前已做的：getPageContext 免克隆、reserve 预读宽度、extractUnits 样式记忆化、观察器自身突变过滤。
- 回归测试：`tests/sessionCancel.test.ts`（会话取消 4 例）；既有 103 例全过（共 107 例）。
- 待复测：大页面（如 en.wikipedia.org）翻译时 CPU / 浏览器响应是否恢复。

### E-003 内容脚本 modulepreload 警告刷屏（噪音，非卡顿主因）
- 来源：构建产物（Vite + @crxjs/vite-plugin 对 content 脚本做代码分割）
- 现象：页面控制台反复出现
  `…modulepreload-polyfill-*.js / storage-*.js was preloaded using link preload but not used …`
  与 `… is not used because it is a cross-world extension resource mismatch`。
- 根因：content 脚本被拆成多个 chunk，Vite 注入 `<link rel="modulepreload">`；但 content 脚本运行在隔离世界，modulepreload 与模块加载跨世界不匹配 → 预加载被浪费并告警。已知问题。
- 次数：多条
- 状态：**已修复·待用户实机确认**（2026-09-14）：`vite.config.ts` 设置 `build.modulePreload: false`，
  构建产物中 preload polyfill 与 modulepreload 链接已完全消失，共享 chunk 的静态导入不受影响。

### E-005 请求并发过高导致服务商封号 —— 【已加请求启动限速】
- 来源：background `TranslateService`（LLM 通道 openai/anthropic/gemini/ollama）
- 现象：用户反馈"发送到服务商的请求并发实在太高，导致服务商禁止了我的账号请求"。
- 根因：LLM 通道此前**只限"并发数"、不限"速率"**——`runConcurrent(limit)` 只控制在途数量（默认 6），响应一快就连续猛发，峰值可达每秒几十个请求，极易触发服务商限流/封号。
- 修复（参照 read-frog 的限流思路）：
  1. **请求启动限速**：`TranslateService.acquireStartSlot()` 用 Promise 链串行化"请求启动时机"，相邻请求启动间隔 ≥ `REQUEST_MIN_INTERVAL_MS`（暂取 500ms，≈2 请求/秒）。**无论并发设多少，启动速率都被钳制**（race-safe，并发调用不抢占时机）。重试也走同一限速。
  2. **降默认并发**：`DEFAULT_SETTINGS.api.maxConcurrency` 6 → **2**（设置页可按服务商额度上调）。
- 说明：googlefree 通道本就有自身限流（并发≤3 + 80ms 间隔），不受影响。
- 状态：**已修复·待用户实机确认**。请求间隔已暴露为设置项（2026-09-14）：设置页「请求间隔（毫秒）」
  （`api.minRequestIntervalMs`，默认 500）可按服务商额度调整；批量解析失败还会先拆 ≤8 段小批量重试，
  最坏请求数从 N 压到约 N/8。
